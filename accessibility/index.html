How it was tested

  • Automated testing with axe-core 4.10.2 (Deque Systems), the engine behind Google Lighthouse and Microsoft Accessibility Insights. Rule sets: wcag2a, wcag2aa, wcag21a, wcag21aa. Run on every portal tab and on each dialog: order detail, proof of delivery, quote document and statement.
  • Scripted manual checks covering keyboard-only operation, focus visibility and order, dialog focus management, error handling, reflow at 320px and WCAG text spacing overrides. Every check was repeated after each fix.
  • Colour contrast measured with the WCAG relative luminance formula for text, status chips, focus rings and form field borders.
  • Criterion-by-criterion review of all 50 WCAG 2.1 Level A and AA success criteria, recorded below.
Issues found during testing were fixed before this report was issued: green status chip contrast (4.41:1 raised to 5.55:1), form field border contrast (1.5:1 raised to 3.54:1), keyboard access to scrollable tables, focus returning to the control that opened a dialog, and keyboard access to individual orders.

WCAG 2.1 Level A and AA criteria

CriterionNameLevelStatusHow the portal meets it
1.1.1Non-text contentASupportsLogos and photos have text alternatives. Product thumbnails sit beside the product name and are marked decorative. Delivery signatures are exposed as images named "Signature of ...". Delivery photos carry captions.
1.2.1Audio-only and video-only (prerecorded)ANot applicableThe portal has no audio or video.
1.2.2Captions (prerecorded)ANot applicableNo video.
1.2.3Audio description or media alternativeANot applicableNo video.
1.2.4Captions (live)AANot applicableNo live media.
1.2.5Audio description (prerecorded)AANot applicableNo video.
1.3.1Info and relationshipsASupportsReal headings, data tables with header cells, form fields grouped in fieldsets with legends, and every field has a programmatic label.
1.3.2Meaningful sequenceASupportsReading order in the code matches the visual order at every screen size.
1.3.3Sensory characteristicsASupportsInstructions never rely on shape, colour, size or position alone.
1.3.4OrientationAASupportsWorks in portrait and landscape. Nothing is locked to one orientation.
1.3.5Identify input purposeAASupportsFields about the signed-in user (contact name, email) carry autocomplete tokens. Client fields deliberately do not, as they describe another person.
1.4.1Use of colourASupportsEvery status colour is paired with a text label, for example "On trial, decision required" and "Arriving from supplier".
1.4.2Audio controlANot applicableNo audio.
1.4.3Contrast (minimum)AASupportsAll text meets 4.5:1 (large text 3:1). Automated contrast checks pass on every view. Status chip colours were darkened during testing to clear the threshold (green chip now 5.55:1).
1.4.4Resize textAASupportsText resizes to 200% without loss of content or function. Layout reflows rather than clipping.
1.4.5Images of textAASupportsNo images of text other than the Max and Silverchain logos, which are exempt.
1.4.10ReflowAASupportsNo sideways page scrolling at 320 CSS pixels (equivalent to 400% zoom). Wide data tables scroll inside a keyboard-focusable region, which WCAG permits for two-dimensional content.
1.4.11Non-text contrastAASupportsForm field borders are 3.54:1 against white and focus rings are 5.89:1. Selected states use a 2px red outline and a tinted background.
1.4.12Text spacingAASupportsTested with WCAG text spacing overrides (line height 1.5, letter spacing 0.12em, word spacing 0.16em, paragraph spacing 2em). No text is clipped or overlaps.
1.4.13Content on hover or focusAASupportsThe portal shows no custom hover or focus pop-ups.
2.1.1KeyboardASupportsEvery action can be done from the keyboard: tabs, catalogue, quote builder, order detail, proof of delivery photos, trial decisions, payments and the quote PDF.
2.1.2No keyboard trapASupportsDialogs keep focus inside while open, as intended, and always close with Escape or the Close button.
2.1.4Character key shortcutsASupportsNo single-key shortcuts.
2.2.1Timing adjustableASupportsNo time limits. Confirmation messages are also reflected in the page itself, for example a new order appearing in Orders.
2.2.2Pause, stop, hideASupportsNothing moves, blinks or auto-updates.
2.3.1Three flashes or below thresholdASupportsNo flashing content.
2.4.1Bypass blocksASupports"Skip to portal content" link as the first focusable element, plus header and main landmarks.
2.4.2Page titledASupportsEach page has a descriptive title.
2.4.3Focus orderASupportsFocus follows a logical order. After a tab or filter updates the screen, focus stays on the control used. Opening a dialog moves focus into it, and closing it returns focus to the control that opened it.
2.4.4Link purpose (in context)ASupportsEvery button and link has a clear name. Repeated buttons name their target, for example "Hire Toilet seat raiser" and "Open order 70540 for Patricia Moore".
2.4.5Multiple waysAASupportsEvery area is reachable from the tab bar, and the catalogue, quote builder and orders all have search.
2.4.6Headings and labelsAASupportsHeadings and field labels describe their content, for example "Client PID" and "Preferred date".
2.4.7Focus visibleAASupportsA 3px focus ring on every focusable element, white on the navy header. Verified on the first 60 tab stops.
2.5.1Pointer gesturesASupportsNo multi-point or path-based gestures.
2.5.2Pointer cancellationASupportsActions fire on release (standard click), never on press.
2.5.3Label in nameASupportsWhere a button has an extended accessible name, it begins with or contains the visible text.
2.5.4Motion actuationANot applicableNo motion-triggered features.
3.1.1Language of pageASupportsPage language set to Australian English (en-AU).
3.1.2Language of partsAASupportsAll content is in English.
3.2.1On focusASupportsFocusing a control never changes context.
3.2.2On inputASupportsChanging a filter or the trial location updates content in place without moving the user elsewhere.
3.2.3Consistent navigationAASupportsHeader, New quote and New order buttons and tab bar are in the same place on every screen.
3.2.4Consistent identificationAASupportsThe same functions use the same names throughout, for example "Client PID".
3.3.1Error identificationASupportsMissing required fields are named in a status message, marked invalid (aria-invalid) and the first one receives focus.
3.3.2Labels or instructionsASupportsEvery field has a visible label. Required fields are marked with an asterisk, explained above the form, and announced as required.
3.3.3Error suggestionAASupportsMessages say exactly what to add, for example "Add the client name, PID and delivery address."
3.3.4Error prevention (legal, financial, data)AASupportsApproving a quote, buying hired equipment, booking a trial return and paying an invoice all need a separate confirmation. Quotes can be edited until they are approved.
4.1.1ParsingASupportsValid, well-formed markup with no duplicate IDs. (This criterion is always satisfied under WCAG 2.1 errata.)
4.1.2Name, role, valueASupportsCustom controls expose their role and state: tabs (aria-selected), colour swatches (aria-pressed), dialogs (aria-modal with a name) and scrollable tables (named regions).
4.1.3Status messagesAASupportsConfirmations and errors are announced through a polite live region (role="status") without moving focus.

Built-in accessibility features

  • Skip link, landmarks and a logical heading structure on every screen.
  • Full keyboard operation, with a visible focus ring and focus kept in place as content updates.
  • Dialogs that take focus, keep it while open, close with Escape and return focus afterwards.
  • Plain English status labels, never colour alone, for example "Arriving from supplier" instead of "Backorder".
  • Required fields marked and announced, with clear error messages and focus moved to the field that needs attention.
  • Responsive layout that reflows to a 320px wide screen, so it works on a phone and at 400% zoom.
  • Large touch targets: buttons are at least 44px high.

Ongoing commitment

  • Every release is re-tested with the same automated and keyboard checks before it reaches Silverchain users.
  • Before go-live Max will complete assistive technology testing with NVDA on Windows and VoiceOver on iOS, and will share the results with Silverchain.
